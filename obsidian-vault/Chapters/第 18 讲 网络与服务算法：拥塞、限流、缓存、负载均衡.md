## 第 18 讲｜网络与服务算法：拥塞、限流、缓存、负载均衡

领域：数据库与分布式算法 · 细讲

<a id="chapter-18-section-01"></a>

### TCP 可靠性与滑动窗口【重点】

TCP 通过序号、确认和必要的重传，使接收方获得可靠且按序的字节流。滑动窗口允许多个数据段在等待确认期间同时在路上，避免每发一点就停下来等。接收方流量控制关心对方是否来得及接收，拥塞控制关心网络本身是否承受得住。它们解决不同瓶颈。可靠传输并不意味着应用业务绝不会重复执行：请求是否已被服务器处理，仍然需要应用层协议判断。

<a id="chapter-18-section-02"></a>

### AIMD、CUBIC 与 BBR【认识】

AIMD 的直觉是逐步增加发送量，发现拥塞后明显退让。CUBIC 采用特定的窗口增长策略，以更有效地利用高速和长距离链路。BBR 尝试估计瓶颈带宽与传播延迟，再据此调节发送，而不是只依赖丢包判断。它们都在处理抢占带宽、延迟和网络稳定性之间的矛盾。不要把某个拥塞控制算法理解成网络加速按钮，具体表现受链路、版本及其他流量影响。

<a id="chapter-18-section-03"></a>

### Token Bucket 与 Leaky Bucket【重点】

令牌桶按一定速度补充令牌，请求到来时消耗令牌；桶能积累一定余量，因此允许短暂突发。漏桶更像以稳定速度排出队列里的请求，把突发流量摊平，队列满时可能丢弃或拒绝。它们用于 API 限流、流量整形和资源保护。允许突发与保证平稳输出是两种不同需求。限制每分钟请求总数，也不等于能防止某一秒突然冲进所有请求。

<a id="chapter-18-section-04"></a>

### Round Robin、Least Connections 与一致性哈希【重点】

轮询依次把请求分配给不同实例，简单且开销低。最少连接优先把新任务交给连接较少的实例，在请求时长差异较大时可能更合理，但连接数量也不是负载的完美替代。一致性哈希把对象与节点映射到可稳定分配的结构，节点增减时减少需要搬迁的键。它常用于分片和缓存定位。三者都涉及分配，但一致性哈希特别重视成员变化后的映射稳定性。

<a id="chapter-18-section-05"></a>

### LRU、LFU 与缓存击穿【重点】

LRU 淘汰最近最久没被访问的数据，利用近期访问可能再次出现的局部性。LFU 淘汰访问频率较低的数据，适合长期稳定热点，但可能把曾经热门、现在过时的对象保留太久。热点缓存恰好失效时，大量请求可能同时涌向数据库。请求合并、互斥重建、提前刷新和过期时间抖动可以缓解不同类型的集中压力。缓存策略既包括淘汰谁，也包括失效后怎样恢复。

<a id="chapter-18-section-06"></a>

### 指数退避、Jitter、Circuit Breaker【重点】

重试失败的服务时逐渐拉长等待时间，叫指数退避；再加入随机抖动，避免所有客户端同一时刻再次冲击。熔断器在连续失败后暂时停止调用，让故障服务有恢复空间，再小规模试探。它们防止一个局部故障被请求风暴放大。重试前还必须确认操作是否幂等，不能把下单失败提示理解为订单一定没有创建。重试策略不是业务去重策略的替代品。
