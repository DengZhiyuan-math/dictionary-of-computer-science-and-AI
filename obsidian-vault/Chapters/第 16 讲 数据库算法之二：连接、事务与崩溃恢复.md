## 第 16 讲｜数据库算法之二：连接、事务与崩溃恢复

领域：数据库与分布式算法 · 细讲

<a id="chapter-16-section-01"></a>

### Nested Loop Join、Hash Join、Merge Join【重点】

嵌套循环连接遍历一张表的记录，再去另一张表寻找匹配。有合适索引且外表很小时，它并不一定慢。哈希连接先把一侧按连接键建立哈希表，再扫描另一侧探测匹配，适合许多等值连接，但内存不足可能需要分批落盘。归并连接利用两侧已经有序的连接键，像合并两个名单一样向前推进。它需要有序输入，已有索引或排序可以提供这种顺序。不存在永远最快的连接算法，数据规模、选择性、索引和内存决定选择。

<a id="chapter-16-section-02"></a>

### Query Optimizer，查询优化器【重点】

同一条 SQL 可以先筛选再连接，也可以先连接再筛选；可以走索引，也可以全表扫描。基于成本的优化器利用统计信息，估计候选方案会处理多少记录、进行多少读取，再选择较便宜的计划。统计信息失真时，它也可能选错。EXPLAIN 展示预计计划，带实际执行统计的分析能进一步检查估计偏差。扫描全表不一定坏：若本来就要读取大多数记录，逐条走索引反而可能更贵。

<a id="chapter-16-section-03"></a>

### Two-Phase Locking 与 MVCC【重点】

两阶段锁在严格规则下先获取锁，再进入释放阶段，用约束并发访问的方式保证一定的事务语义，代价是阻塞和死锁风险。MVCC 保留数据的多个版本，让读取者根据快照选择可见记录，减少某些读写互相阻塞。MVCC 不意味着完全没有锁，更不自动等于可串行化。两个事务各自看到合法快照，却共同造成跨记录约束被破坏，是理解写偏差的典型入口。

<a id="chapter-16-section-04"></a>

### Optimistic Concurrency Control，乐观并发控制【认识】

乐观并发控制允许事务先执行，提交前再检查相关数据是否被别人改过；若冲突则回滚或重试。它适合冲突较少的场景，避免所有操作预先排队拿锁。版本号比较是常见直觉：更新时必须确认数据还是我读到的那个版本。冲突频繁时，重做成本可能很高。乐观与悲观不是态度问题，而是把冲突处理成本安排在操作之前还是提交附近。

<a id="chapter-16-section-05"></a>

### WAL、Checkpoint 与恢复【重点】

预写日志要求在相关数据页的修改持久化之前，先把必要日志可靠写好，使系统崩溃后有机会重做已经提交的操作。具体引擎还会结合撤销、版本管理等恢复机制。检查点记录一个可作为恢复起点的状态，避免重启时从很久以前扫描所有日志。不要把写入应用日志等同于数据库的持久性保证。必须讨论日志是否真正落到可靠存储，以及崩溃发生在提交流程的哪个位置。

<a id="chapter-16-section-06"></a>

### 2PC 与 Saga【认识】

两阶段提交让参与者先准备，再由协调者通知统一提交或中止，目的是跨资源保持提交结果一致。经典形式会受到协调者故障造成阻塞的影响。Saga 把长事务拆成多个本地事务，失败时执行业务补偿，例如释放预订而不是倒转所有外界影响。两者不是同等语义的快慢版本。Saga 接受中间状态，并要求补偿设计；两阶段提交追求另一种原子提交边界。

<a id="chapter-16-section-07"></a>

### 案例 27：事务：转账中途失败怎么办

场景与输入：账户 A 有 100，B 有 20，转账 30，预期结果 A=70、B=50。

手算第 1 步：若先扣 A 再加 B，恰在两步之间进程崩溃，裸写入可能只留下扣款。

手算第 2 步：将两次更新纳入同一事务，提交前失败时应回滚；成功提交后，两次更新共同构成已提交结果。

手算第 3 步：还应通过条件更新或合适的并发控制检查余额，避免两个同时转账都基于过时余额批准。

结果与解释：原子性关注一组操作共同成功或失败；隔离性处理并发交错；持久性依赖提交与恢复机制。

易错点与边界：只是把两个语句写在一起不等于事务；跨数据库或外部支付还涉及其他协议与幂等设计。

改变条件再想一想：数据库已提交但客户端没收到响应，直接重试一定安全吗？

自测参考：不一定，可能重复转账；需要业务幂等键或可查询的操作状态。
