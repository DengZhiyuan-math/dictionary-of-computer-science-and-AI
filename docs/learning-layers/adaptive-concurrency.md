# Adaptive Concurrency · 服务并发上限的反馈控制

概念编号：`concept:adaptive-concurrency` · [网站双语阅读](https://zhiyuan-deng.pages.dev/dictionary/topic/concept/adaptive-concurrency/)

## 第一层：概念入门 · 知其然

### 请求速率与在途数量

一个请求从被接纳到完成期间属于在途请求。并发上限限制同时有多少请求尚未结束；每秒请求速率限制一段时间内来了多少请求。处理时间变长时，即使每秒到达数量不变，在途数量也可能增加。


### 定义

自适应并发限制根据已经观察到的延迟、失败或利用情况，调整允许同时在途的请求数。它是一种反馈控制：利用服务运行结果修正后续接纳，不是预先固定一个永远适用的容量，也不是把所有排队请求立即取消。

### 理解定义中的术语与关系

#### 延迟为何是信号而不是诊断结论

请求变慢可能因为等待资源，也可能因为任务本身变重、网络变化或下游变慢。控制器可在拥塞迹象增强时降低接纳上限，观察系统是否恢复。具体规则还需说明观测窗口、上下限和怎样处理错误样本，不能把某个延迟比值直接当作真实排队人数。

### 概念边界与常见混淆

反馈有观测延迟与噪声，过度调整可能引起振荡。不同服务不能照搬同一阈值；延迟改善也不应以无解释的大量拒绝或错误为代价。

### 先看一个例子

设当前上限十个请求，已有十个在途。教学策略规定：最近一段时间明显变慢，就把后续上限降到八。此时已有十个请求不会凭空消失；系统暂不接纳新请求，等已有请求结束，使在途数量回到新上限以内。是否变快仍要由后续观测判断。

### 理解练习

#### 1. 并发与每秒速率

并发上限十，是否意味着每秒最多处理十个请求？

<details><summary>答案与解释</summary>

不是。上限限制同时未完成的数量。若请求很快，可以一秒完成许多轮；若很慢，一秒可能连一轮也没完成。还需要服务时间信息。

</details>

#### 2. 降低上限的即时含义

已有十个在途，上限降到八，是否必须马上取消两个？

<details><summary>答案与解释</summary>

不必。通常可以停止后续接纳，等待已有请求自然完成。取消与否属于另外的协议和服务策略，不能由上限数字自行推出。

</details>

#### 3. 为什么不能只看延迟

控制器降低上限后延迟下降，就能断言服务整体改善吗？

<details><summary>答案与解释</summary>

不能，还要看完成量、拒绝率、错误率及实际任务是否可比。若仅靠拒绝大部分工作得到更低延迟，就没有回答整体服务目标是否达成。

</details>

### 原有解释与进一步例题


### 定义与应用范围

自适应并发限制器根据已经观察到的服务延迟、利用率或丢弃等反馈，调整同时在途的请求数。它把背压落到请求入口，目的是控制排队；并发上限是请求数，不能当作每秒请求速率。


### 参数、公式与边界

在本页讨论的固定基线教学口径中，上限为 L、无排队基线延迟为 R₀、当前延迟为 R，且 R≥R₀>0，排队量估计为 \(\widehat q=\lceil L(1-R_0/R)\rceil\)。这只是反馈信号，不能单凭它推断真实队列。实际更新还要声明阈值、平滑、上下界和基线探测规则，不能凭公式臆造完整控制策略。


### 例子

L=20、R₀=10 毫秒、R=20 毫秒时，估计排队量为 10。控制器可以按事先设定的策略降低后续准入，但已经进入系统的请求不会因此消失。若 R₀ 失真，估计也会失真；处理时间较长与排队较多需要额外观测来区分。


### 适用边界与常见误解

The queue estimate is a model, not a measured count of waiting requests. A concurrency cap is distinct from a request-rate quota. This pinned open-source implementation does not establish Netflix's current production configuration.

### 概念辨析

- [Token Bucket / Rate Limiting](token-bucket.md)：令牌桶控制准入速率与突发额度；并发限制控制同时在途数量。相同请求速率可对应不同并发。
